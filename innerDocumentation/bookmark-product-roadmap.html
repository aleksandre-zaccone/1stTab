One purpose, several related capabilities

Help users save, organize, and retrieve their Chrome bookmarks.

Product promise

Find the link you saved. Keep folders tidy. Add context to a bookmark. Preserve your library when making changes.

Suggested listing: “1stTab — Bookmark Manager. Save pages, organize folders, add tags and notes, and quickly find your saved links.” Advertise each feature only after it ships.

Release boundary

Use an on-demand bookmark manager and a bookmark-only side panel. New tabs open the bookmark manager, following the updated product preference.

Exclude independent dashboard widgets, browser administration, web search, and general AI tools. This is a proposed conservative scope, not a claim that every excluded feature is forbidden.

Google allows several related features under one narrow purpose. Eligibility depends on the final behavior, permissions, disclosures, package, and review—not the feature count. No approval guarantee is implied.

Refactoring roadmap

Sequence by acceptance gates rather than fixed dates. Implementation estimates require resolving the incomplete checkout and choosing the migration behavior.

01
Scope gate

Define the release boundary

  1. Use the purpose statement below in the product specification and store submission. Record every shipped feature and its bookmark-related justification.
  2. Configure chrome_url_overrides.newtab to manager.html. The same bookmark library opens in new tabs, on demand, and in the side panel.
  3. Remove weather, clocks, quotes, finance, tasks, calendar, hardware monitoring, media controls, tab-session management, and general-purpose AI from the extension release. These can remain separate web-app ideas.
  4. Archive the older ai_product_roadmap.md as superseded: page-wide assistants, screenshots, translation, writing tools, and video summaries are outside this bookmark roadmap.

Exit: every visible action supports saving, organizing, finding, or preserving bookmarks.

02
Foundation gate

Consolidate the bookmark core

  1. Extract a bookmark repository from data.jsx using chrome.bookmarks as the source of truth. Share it between manager-app.jsx and the bookmark-only panel.jsx.
  2. Extract metadata storage, search, import/export, and reusable tree/list components. Reconcile the overlapping manager.jsx and manager-app.jsx implementations before deleting legacy code.
  3. Use bookmark events to refresh both surfaces; handle deleted items, folder moves, API errors, and browser-managed/non-editable nodes. Do not assume root folder IDs are always 1 and 2.
  4. Create a versioned, repeatable migration for nt.bookmarkMeta. Snapshot old metadata, preserve descriptions/tags/pins, remove orphan references, and retain legacy data until migration succeeds.
  5. Keep large metadata in chrome.storage.local rather than one growing sync item. Chrome bookmark syncing and extension metadata syncing are separate behaviors; do not promise cross-device tags in the first release.

Exit: editing either surface updates the other; migration can retry without losing bookmarks or metadata.

03
Implementation gate

Replace the dashboard shell

  1. Make manager.html the main library; refactor panel.jsx to bookmarks only. Limit settings-app.jsx to appearance, bookmark preferences, backup, and data controls.
  2. Refactor background.js to toolbar/shortcut behavior and bookmark-only operations. Remove media tracking, unrelated message handlers, calendar/tasks/finance calls, and automatic promotional bookmark seeding.
  3. Remove dashboard app.jsx and unrelated widgets from the release dependency graph. Preserve old source during the transition; strip it from the shipping ZIP.
  4. Replace the build.sh hard-coded dashboard file list with explicit bookmark entry points and a package asset allowlist. Resolve missing tokens.css/theme-bootstrap.js dependencies or replace their references with included local assets.
  5. Use local assets and bundled code. Replace remote favicon requests with a bundled fallback for launch; evaluate Chrome favicon access separately if needed.

Exit: packaged manager, panel, settings, and service worker load without missing resources or console errors.

04
Release gate

Ship the local bookmark MVP

  1. Implement the six Launch feature groups above, including confirmed deletes, bulk-operation previews, and safe additive import.
  2. Test create/edit/move/delete and cross-surface events, duplicate handling, import validation, export round trips, migration retry, and metadata restoration. Include Unicode, invalid URLs, nested folders, and managed nodes.
  3. Validate keyboard focus, labels, contrast, narrow screens, empty states, and the large-library fixture. Verify offline library access and no network transmission during ordinary bookmark operations.
  4. Inspect the packaged ZIP and manifest, install it unpacked in Chrome, and exercise the toolbar, side panel, shortcut, restart, and service-worker lifecycle.
  5. Update manual.html, privacy.html, store screenshots, permission explanations, and website copy to match the shipped product. Supply reviewer instructions for every advertised capability.

Exit: reproducible package, passing essential checks, accurate disclosures, and a complete reviewer walkthrough.

05
Separate release gate

Add bookmark-specific intelligence

  1. Ship cleanup and recovery first. Keep basic bookmark management usable without AI or an account.
  2. Introduce AI only after the local release is stable: choose one provider first, request its host access on enablement, show the exact data fields sent, and keep keys out of backups and logs.
  3. Treat AI output as untrusted suggestions. Validate referenced bookmark IDs, URL schemes, and folder targets; require a preview before mutations.
  4. If cloud backup is added, isolate its permissions and OAuth scopes, define conflict/restore behavior, test denied access, and disclose provider retention and deletion practices.
  5. Recheck policies and the actual rejection notice before each submission; feature relatedness is a design argument, not an approval guarantee.

Exit: optional services are consented, narrowly scoped, failure-tolerant, and independently reviewable.

Reposition the website with the extension

First: a clear product home

Proposed direction for 1sttab-app.web.app: bookmark-focused messaging, real feature screenshots, install instructions, a manual, privacy policy, changelog, and support. Explain exactly what stays local and what optional services transmit.

Do not list planned AI/cloud capabilities as already available. The website’s current contents were not inspected successfully.

Later: a companion library

A web library can initially work with user-imported exports. A hosted website cannot directly read Chrome’s bookmark tree; live integration requires a designed extension-to-service connection with authentication and explicit consent.

Keep a broader productivity app separately positioned if desired. The extension must provide useful bookmark management itself, rather than only launching the website.

Suggested packaging

Core: local bookmark management, search, metadata, cleanup, and export. Optional Plus: bookmark-specific AI and cloud backup after their separate release gates. Do not gate users’ ability to export their own data.

Policy basis & review checklist

  • Google: single-purpose FAQ — related capabilities may share a narrow focus; unrelated permissions undermine that argument.
  • Google: Web Store program policies — minimum access, accurate disclosures, secure handling, useful and working functionality.
  • Google: activeTab permission — temporary access after a qualifying user gesture.
  • Google: rejection troubleshooting — use the actual violation ID when preparing a resubmission.

Before submitting: demonstrate every feature, justify every permission, confirm no unrelated handlers remain, verify all bundled assets, disclose third-party data transfers, and align website, listing, and extension behavior. Google makes the final review decision.
