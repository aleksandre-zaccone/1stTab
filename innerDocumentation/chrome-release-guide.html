1. Set up access

You need GitHub repository settings access and the Google account that owns our existing store item.

Setup 01

Identify our existing extension

Sign in to the Chrome Web Store dashboard. Enable two-step verification. Find the publisher ID under Publisher → Settings.

Our extension ID: bigolehnkpljdbocpkljjmkkocefinbh. Keep using this item so updates reach existing users.

Setup 02

Create Google publishing credentials

  1. In Google Cloud Console, select a project and enable Chrome Web Store API.
  2. Configure the OAuth consent screen with an app name, support email and contact email. For External testing, add the publisher account as a test user.
  3. Create an OAuth client of type Web application.
  4. Add this authorized redirect URI: https://developers.google.com/oauthplayground.
  5. Keep its client ID and client secret for GitHub.

Console labels may appear under Google Auth Platform → Branding, Audience and Clients.

Setup 03

Generate the refresh token

  1. Open OAuth Playground → gear → Use your own OAuth credentials. Enter that client ID and secret.
  2. Authorize scope https://www.googleapis.com/auth/chromewebstore using the store-owning account.
  3. Exchange the authorization code and save the refresh token.

Google’s illustrated setup instructions →

For ongoing releases: External OAuth apps in Testing issue refresh tokens that expire after seven days for this scope. Move the OAuth app to Production, complete any requirements Google presents, then generate a new token. This is separate from publishing the extension. Token expiration reference.

Setup 05 · also review before each release

Complete the store listing

The workflow uploads the extension package. Listing text, images and declarations are maintained in the dashboard.

  • Store listing: description, category, language, screenshots, icon and promotional assets.
  • Privacy practices: single purpose, permission justifications, data disclosures, certifications and privacy policy URL.
  • Distribution: countries and visibility.
  • Reviewer notes: explain relevant changes. For the v2 resubmission, explain that search only searches saved bookmarks and the extension does not change the default search provider.

Our current product purpose is bookmark management. Google Drive and cross-account sync are upcoming; do not describe them as available.

2. Release a new version

Example below: 2.0.1. Use it only if it is higher than the latest uploaded store version.

Release 01

Update, test and merge

  1. On a feature branch, set version to 2.0.1 in both manifest.json and package.json. Update the version label in privacy.html and relevant release notes.
  2. Open a pull request targeting main. The QA workflow runs tests and builds 1stTab-bookmarks.zip.
  3. Test the built extension in Chrome: new tab, bookmarks, search, folder moves, settings and side panel.
  4. Review and merge the PR after checks pass.

A merge does not publish. The workflow also does not increase version numbers automatically.

Release 02

Tag the reviewed commit

From a clean checkout of this repository, after your release PR is merged:

git switch main
git pull --ff-only origin main
git tag v2.0.1
git push origin v2.0.1

Confirm the checked-out commit is the one you intend to release before tagging. The tag must match both source versions and point to a commit included in main. Do not overwrite a tag already used for a release.

Release 03

Run the check without uploading

  1. Open Actions → Publish to Chrome Web Store.
  2. Select Run workflow, branch main.
  3. Enter tag v2.0.1 and operation check.
  4. Run it and wait for all steps to pass, including Check Chrome Web Store access.

This validates the tag, runs tests, builds the package, saves a downloadable artifact and reads store status. It does not upload or submit. Resolve any failure before the next step.

Release 04

Publish the GitHub Release

  1. Open GitHub → Releases → Draft a new release.
  2. Choose the existing tag v2.0.1.
  3. Enter a title such as 1stTab 2.0.1 and notes explaining changes and fixes.
  4. Leave pre-release unchecked. Select Publish release when ready to submit to Google.

Publishing a stable GitHub Release starts the workflow automatically. Saving a draft does not start it. The workflow builds from the tag; it does not upload a ZIP attached manually to the GitHub Release.

Choose one submission route: publishing the GitHub Release is the normal route. Manually running the workflow with submit is an alternative. Do not use both for the same version, or trigger either if that version was already uploaded manually.

Release 05

Follow the run, then Google’s review

The release job performs these steps in order:

  1. Validate the tag, source versions and membership in main.
  2. Run tests and build dist/1stTab-bookmarks.zip.
  3. Save the verified package as a GitHub Actions artifact.
  4. Check Google access, upload the package and request publication.
  5. Read the immediate submission status.

Open the store dashboard to follow review. A successful workflow means the submission completed, not that Google approved it. The API route publishes after approval under the existing visibility settings. Our workflow does not monitor the review continuously. API publication behavior.

3. If something fails

Check the failed Actions step and the current store draft before retrying.

Google authentication fails: HTTP 400 or 401

Check that the client ID, client secret and refresh token belong together. Repeat Setup 03 using the store owner’s account, update the secrets and rerun check. If the token expires after seven days, check the OAuth app’s Testing status. The last known v2.0.0 run stopped here before uploading.

Access denied or item not found: HTTP 403 or 404

Verify the API is enabled, the OAuth scope is correct, the publisher and extension IDs match the item, and the authorizing account has access to that publisher.

Version mismatch or version already uploaded

Compare the tag with both source version fields and check the dashboard’s Package tab. A new package needs a higher version. Fix source versions through a PR and create a new tag; do not move an existing release tag.

Upload succeeded but submission failed

Open the existing uploaded draft. Complete missing listing or privacy details and submit that draft in the dashboard. Do not blindly rerun the uploader with the same version. If visibility changed, Google may require one manual publication with that visibility before API publishing resumes.

Need to upload the package manually?

Download the verified Actions artifact and extract its outer ZIP. In the existing store item’s Package tab, upload the inner 1stTab-bookmarks.zip. Its root must contain manifest.json. Complete the dashboard details and select Submit for Review. Do not then publish a GitHub Release that triggers a duplicate upload.

Google rejects or takes down the update

Read the exact policy notice, fix the stated problem and prepare a corrected version. A green build cannot guarantee policy approval. For our bookmark-only release, submit the default package rather than the optional integration build.
